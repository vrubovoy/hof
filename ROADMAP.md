# Hof — дорожная карта после M10

> **Статус:** проектный документ, версия 0.1 от 30.10.2026. **Не является утверждёнными GitHub Issues и не разрешает автоматически выполнять работы.**
>
> **Исходная точка:** тег `m10` опубликован; проверенная сборка M10 работает на публичном сервере, приложение уже используется реальными людьми. Официальный выпуск **1.0.0 ещё не объявлен**. Проверенный коммит при приёмке M10: `f25e5dad6b5ca89815bf18e3537bba29b5d30363` (соответствие текущей production-сборки перепроверять перед изменениями).
>
> **Принцип:** *Complexity must be earned*. Выбираем минимальную архитектуру, обеспечивающую нужный UX, надёжность и возможность развития служб. Технология — средство, а не цель.

## 0. Неприкосновенные правила с M11

1. **Production-БД содержит реальные данные.** Ни при разработке, ни при обновлении запрещено удалять или пересоздавать рабочие БД, таблицы, volumes и пользовательские записи ради «чистой установки». Разрешены только контролируемые миграции с сохранением данных. Исключения требуют отдельного, явного и предметного разрешения владельца.
2. **До изменения production:** резервная копия, проверяемое восстановление на изолированном стенде, план миграции, откат приложения и оценка совместимости схем. Не считать откат контейнера откатом данных: миграции должны учитывать это отдельно.
3. **Безопасный цикл:** одна ограниченная Issue → отдельная ветка → тесты → независимое ревью → PR → merge → одобренное развёртывание. Никаких автоматических удалений БД и безусловных деплоев при каждом push.
4. **VPS и VPN:** не трогать соседние службы, общие ресурсы, DNS, firewall и рабочий VPN без отдельного разрешения. Новые внешние покупки (домен, сервер) выполняет владелец либо согласует отдельно.
5. **Сервер — источник истины:** Hono/PostgreSQL и серверная авторизация, права доступа и денежные транзакции остаются авторитетными. Клиентские анимации, React и SPA не должны определять успешность операций.
6. **Регрессии:** сохранять поведение прямых URL, обновления страницы, истории, logout, защиты от двойной отправки, `Cache-Control: no-store` для защищённого HTML и CSP. Режим без JavaScript — сохранять там, где это практически и технически оправданно; отказ от существующего контракта возможен только после явного решения.
7. **Производительность измеряется:** сравнивать по устройствам и условиям с базовой M10, включая первую загрузку, объём статики, CPU, память, плавность анимаций и скорость навигации. Не добавлять тяжёлые фреймворки/движки/зависимости без измеренного выигрыша.
8. **Комментарии, документация и коммиты** — по-русски; технические имена, пути, идентификаторы и API остаются как требуется в коде. Объяснять *зачем*, а не пересказывать очевидное *что*.
9. Новые замечания во время тестирования записывать в backlog с воспроизводимым сценарием и влиянием. Не расширять текущую Issue автоматически. Исключение — проблемы безопасности и сохранности данных.

## 2. M11 — безопасная эксплуатация production и CI/CD

**Зачем:** Hof уже используется людьми. Риск потерять БД опаснее косметических недостатков интерфейса.

**Предлагаемые отдельные Issues:**

- **M11.1. Защита данных:** автоматизированные бэкапы PostgreSQL, контроль сроков хранения, проверка восстановления в отдельную БД, документированный процесс миграций и отката. Политика «не удалять production-БД» — в правилах разработки и эксплуатации.
- **M11.2. CI:** GitHub Actions на PR и `main`: форматирование, линтер, типы, тесты, Docker build. Статус проверки обязателен для merge, где это возможно.
- **M11.3. CD:** образ в реестре по SHA/digest; отдельная учётная запись/минимальные права для деплоя; на сервере `pull`, контролируемые миграции и обновление контейнера; **ручное одобрение production**; отсутствие `git pull`/сборки исходников на VPS.
- **M11.4. Проверка здоровья:** добавить `/healthz` (лёгкая проверка живости) и определить отдельно, нужен ли readiness-check зависимостей; подключить к процессу развёртывания без разглашения внутреннего состояния.
- **M11.5. Эксплуатация:** дисковое пространство, логи, ротация, сертификаты, мониторинг OOM/рестартов. Не запускать глобальный Docker cleanup.
- **M11.6. Отзыв доступа:** отдельно исследовать задержку завершения чужой сессии после изъятия ключа и корректное сообщение пользователю; не путать неверные учётные данные с отозванным доступом.
- **M11.7 (опционально).** План отдельного VPS/домена: требования, бюджет, DNS/TLS, миграция **с данными** и rollback. **Не блокирует** остальные пункты M11, пока решение об аренде не принято.

**Готово, когда:** PR проходят CI, новая сборка доставляется без ручной сборки на VPS, backup реально восстанавливается, деплой не уничтожает данные, контрольный `/healthz` доступен, отзыву доступа соответствует понятный UX. Домен/новый VPS — отдельное решение владельца.

## 3. M12 — качество графики, ассетов и первого входа

- Новые **мобильные** версии картин для страниц с засветлением справа; не маскировать дефект случайными CSS-фильтрами.
- Читаемость текста на знамени и взаимодействие со скроллом.
- Исправить «плавающую стену» под флагами: неподвижная архитектура не должна двигаться вместе с тканью.
- Улучшить знаки/иконки мешков; при необходимости перерисовать или создать новые ассеты.
- Оптимизировать критические изображения первого экрана; выбрать подходящие форматы, размеры, `srcset`/`picture`, приоритет загрузки, lazy-loading только для некритичного декора, версионированный кэш статики. Учитывать механизм `/forget.css`.
- Разобрать текущие лаги анимаций/переходов: измерить baseline; исправить локальные проблемы CSS/слоёв, не пытаться здесь решать полностью всю MPA-навигацию — это M14–M16.
- Убрать выделение/drag декоративных картинок, **не запрещая** выделение полезного текста и взаимодействие с контролами.

**Готово, когда:** нет засветления на телефоне, тексты читаемы, стена неподвижна, первый экран загружается измеримо быстрее M10, визуальные эффекты стабильны, без ухудшения работы на бюджетных устройствах.

## 4. M13 — UX Core и Säckel без большого переписывания

- Увеличить толщину тонких линий Säckel, контраст/насыщенность слишком тонких текстов; сохранить стиль.
- Расширить поле «Заметка» при добавлении дохода.
- Выбирать значок/знак мешка **в форме создания**, переиспользуя серверную валидацию и значения формы редактирования.
- Единый формат сумм с пробелами между разрядами; без перевода денежной арифметики на floating point. Отображение и ввод проектировать отдельно.
- Удобный выбор даты: вначале оценить нативный календарь, собственный писать только при доказанном недостатке.
- Переход «назад к предыдущей странице» с безопасным fallback при прямом открытии адреса; не использовать безусловно `history.back()`.
- Cooldown/ограничение накладывающихся звуков котов, без задержки важных кликов.
- Уточнить поведение кота на входе и сервисных страницах: анимация по умолчанию может быть включена только как осознанное правило; **явное отключение пользователем и `prefers-reduced-motion` нельзя игнорировать**.
- Исправить текст и задержку после изъятия ключа (серверная часть диагностики — M11.6).
- Проработать прокрутку с явными требованиями для ПК и телефона; общую SPA-историю прокрутки довести в M15–M16.

**Готово, когда:** ключевые действия выполняются без обходных шагов, сообщения понятны, формы удобны на телефоне, все старые финансовые сценарии и UI = SQL сохранены.

## 5. M14 — экспериментальный прототип React/SPA

**Решение пока не принято:** пользователь хочет React и максимально плавную SPA; нужно подтвердить на прототипе, что конкретная схема не ухудшает быстроту и безопасность.

**Минимальный вертикальный сценарий:** Двор → Säckel → Мешки → Летопись → Двор; также одна серверно подтверждённая денежная операция. Включить прямой URL, reload, back/forward, выход, смену пользователя, обработку ошибок.

**Проверить:**
- Навигацию без уничтожения браузерного документа, непрерывное воспроизведение музыки и эффекта звука.
- Настоящее перелистывание или сопоставимо качественный направленный переход; стабильность клякс и слоёв.
- React + минимальный роутер vs более лёгкий способ интеграции; не вводить автоматически Next.js, Redux и отдельный backend.
- Авторизация, защита от устаревших финансовых данных, no-store, CSP, cookie, logout/bfcache, поведение при отключённом JS (или явно согласованную деградацию).
- Размер начального JS, LCP, INP, CLS, нагрузку CPU, память, fps на телефоне относительно M10/M12.

**Готово, когда:** есть рабочий прототип и короткая ADR (architecture decision record): выбранная технология, схема API/SSR, границы миграции, риски, план отката и результаты замеров. **Если выигрыша нет — не переписываем весь Hof ради React.**

## 6. M15 — новая оболочка и Core UI

- Перенести только утверждённую в M14 клиентскую часть в постоянную оболочку; Hono, PostgreSQL и проверка прав остаются на сервере.
- Постоянная музыка, настройки, общие декорации и навигация; корректный жизненный цикл звука.
- Стартовая страница для вошедшего пользователя.
- Страница «О программе»: разработчик, контакты, действительная версия приложения, художественное оформление.
- Переходы Двор → службы, анимации дверей, открытие/закрытие, скролл/история и возврат на предыдущий адрес.
- Знамя должно разворачиваться **при каждом навигационном входе на Двор** по утверждённому правилу, но не при каждом ререндере React; исправить движение и привязку к прокрутке.
- Доступность, мобильное взаимодействие, отказоустойчивость на прямой ссылке и после reload.

**Готово, когда:** Core стабилен, музыка при навигации не прерывается, стили и движения соответствуют прототипам, серверная безопасность и старые записи сохраняются.

## 7. M16 — полноценная SPA-навигация Säckel

- Казна, Мешки, Летопись, карточки и формы: перейти к смене представлений **без полной перезагрузки страницы** для внутренних переходов.
- Кляксы и постоянные декоративные элементы остаются там же при переключениях.
- Перелистывание, transitions, звуки и анимации без заикания и блокировки основного потока.
- Сохранение/восстановление контекста, позиции прокрутки, адресов и истории.
- Проверка всех финансовых операций и прав: одна отправка → один серверный результат; клиент не подменяет баланс; UI = SQL во всех режимах и при ошибках.

**Готово, когда:** навигация между Мешками и Летописью плавная, без reload и смещения клякс; сохранена надёжность финансов и производительность не хуже согласованных порогов.

## 8. M17 — ревью, рефакторинг, чистота и документация

Этот Milestone **разделить на независимые Issues**, не сваливать в один запрос.

- **Архитектурное ревью:** большие `app.ts` разделить по ответственности (маршруты, шаблоны/компоненты, авторизация, бизнес-операции), а не по формальному лимиту строк. Сохранить тесты и публичные контракты.
- **Комментарии и шапки:** убрать избыточные объяснения и ссылки, разработать единый компактный заголовок файла в духе STM32CubeMX: назначение и модуль, дополнительные поля только по необходимости. Не документировать очевидное ради объёма.
- **Очистка репозитория:** доказательно неиспользуемые скрипты, дубликаты ассетов, временные файлы и устаревшие материалы; перед удалением проверять ссылки/сборку. История Git сохраняется.
- **Developer Reference:** подробное API/типы/инварианты/архитектура; выбрать подходящий для TypeScript генератор, при необходимости выпускать PDF через LaTeX.
- **Developer Guide:** небольшой набор поддерживаемых Markdown-файлов и сборка обзорного PDF через Pandoc.
- **User/Admin Guide:** структура, сценарии, места под скриншоты; красивые пользовательские PDF со снимками и подписями собирает сам владелец.
- **OpenAPI/Swagger:** документировать *реальные стабильные программные API*, прежде всего нужные клиенту/интеграциям. Не представлять все внутренние SSR-страницы как публичный API.

**Готово, когда:** структура читаема и проверяема, docs соответствуют коду, ничего нужного не удалено, полная регрессия проходит. Не считать автоматически сгенерированный объём документации мерой качества.

## 9. M18 — приёмка и официальный Hof 1.0.0

- Заморозка возможностей; закрытие критичных и заметных UX-дефектов из согласованного списка.
- Chrome/Firefox/Safari на реальном Mac/iPhone и мобильных устройствах; размер окна, 200 % масштаб, клавиатура и touch.
- Безопасность доступа и logout, тестирование новых ролей, UI = SQL, совместимость миграций, восстановление из backup, обновление без потери данных.
- Сравнение производительности с M10 и M12; отсутствие постоянных лагов переходов, визуальных прыжков и обрывов музыки при внутренней навигации.
- Проверка скрипта выпуска и CD по SHA/digest; аудит секретов, лицензий и документации.
- Только после приёмки — отдельное решение владельца об официальном теге `v1.0.0` и публикации.

**Готово, когда:** версия пригодна для регулярного использования реальными пользователями, сценарии подтверждены на действительной инфраструктуре без разрушения данных.

## 10. После 1.0.0: M19–M21+

### M19 — установщик собственного сервера Hof

Клиент-установщик по аналогии с AmneziaVPN: пользователь указывает сервер и предоставляет необходимую конфигурацию/ключ доступа, выбирает службы, приложение настраивает сервер и обновления. Отдельно спроектировать хранение секретов, подключение, права, обновление без потери БД и откат. **Не добавлять универсальную платформу хостинга до появления реального сценария установки.**

### M20 — новые службы и модульность

Контракт независимых служб на основе опыта Säckel: подключение, маршруты, права, схема хранения и атомарность совместных операций. Делать платформенные абстракции тогда, когда вторая конкретная служба выявит потребность.

### M21+ — нативные клиенты

Раздельные нативные клиенты платформ с существующим сервером; сначала стабильный API/авторизация, затем один клиент и измерение реальной пользы. Не смешивать с миграцией веб-клиента на React.
