# Эксплуатация Hof

Правила сохранности данных, установка на сервер, сертификат, резервные копии, восстановление,
обновление, откат и диагностика.
Как устроен Hof — [ARCHITECTURE.md](../ARCHITECTURE.md), разработка — [README.md](../README.md).

Команды выполняются от root в каталоге Hof `/opt/hof`, где лежат `compose.yaml` и `.env`, если не
сказано иное. Аварийная остановка — `docker compose stop` в этом каталоге: она останавливает только
контейнеры Hof, данные остаются в томе `hof_pgdata`.

## Требования

- Linux с Docker Engine и Docker Compose v2, `git`, `openssl` и `certbot`. Проверено на Ubuntu
  24.04 x86_64: Docker 29.1 и Compose 2.40 из пакетов Ubuntu (плагин `buildx` не нужен), certbot
  2.9 из пакета `certbot`.
- Публичный IPv4, домен с A-записью на него, порты 80 и 443 свободны и доступны снаружи. IPv6 Hof
  не обслуживает: AAAA-записи у домена нет.
- Память. На сервере с 1 vCPU и 961 MiB (2026-10-19, двор ещё не основан): PostgreSQL — 5–14 MiB
  своей памяти и 20 MiB общей, остальное до 112 MiB — кэш файлов, который ядро вытесняет; Hof —
  45–50 MiB (пик 66); nginx — 3 MiB (пик 4). Больше всего памяти берут входы: Argon2 считает в
  четырёх потоках, и на ноутбуке после 11 одновременных входов Hof держал 158 MiB (пик 164).
- Диск: образы — около 0,8 ГБ (PostgreSQL 457 MB, Node с кодом Hof около 266 MB, nginx 68 MB), том
  с пустой базой — 64 МБ, копия пустой базы — 13 КБ. Код Hof с M10 занимает в образе 40 MB вместо
  12 MB: звуки, музыка и кадры эффектов (замер слоёв на ноутбуке arm64, где весь образ — 319 MB).
  На время обновления нужно место ещё под один образ Hof, кэш сборки и копию.
- Время на том же сервере: загрузка образов — 19 с, сборка образа Hof — 4 с, запуск — 7 с; вся
  установка от `git clone` до работающего стека с сертификатом — около 4 минут.

## Правила сохранности данных

В production-базе реальные бюджеты. Правила действуют всегда, исключение — только отдельное явное
решение владельца.

**Том PostgreSQL.** На действующей установке том `hof_pgdata` не удаляют и не пересоздают,
`docker compose down -v` не выполняют, независимо от содержимого базы: пустая таблица `users` не
доказывает отсутствие важных данных. Заведомо временную установку очищают по разделу «Очистка
временной установки».

**Миграции.**

- Применённые файлы неизменяемы: их не правят, не переименовывают и не удаляют. Файл, который не
  применился ни на одной установке, можно исправить.
- `schema_migrations` вручную не меняют.
- Новые изменения по возможности совместимы с предыдущим кодом. Несовместимые выполняются поэтапно;
  дополнительные этапы нужны только там, где дают реальную безопасность.
- Число миграций в выпуске не ограничено, совместимое изменение не требует отдельного выпуска.

**До развёртывания выпуска с миграциями.**

- Issue или PR выпуска указывает файлы, совместимость с прежним кодом и способ вернуть прежнее
  поведение. Если откат приложения невозможен, это указывается явно.
- Новым кодом проводят учения на свежей копии (раздел «Проверить копию»).
- Перед первым обновлением на код с проверкой при старте список применённых миграций сверяют только
  чтением. Ожидаются 4 имени: `core/001_users.sql`, `core/002_sessions.sql`,
  `saeckel/001_pouches.sql`, `saeckel/002_operations.sql`. Лишнее имя не даст новому Hof стартовать.

  ```sh
  docker compose exec -T postgres psql --username=postgres --dbname=hof -At \
    -c "SELECT 'core/' || name FROM core.schema_migrations UNION ALL SELECT 'saeckel/' || name FROM saeckel.schema_migrations ORDER BY 1"
  ```

**Проверка при старте.** До первого изменения схемы в любом модуле Hof сравнивает применённые
миграции каждого модуля со своей папкой, под ролью этого модуля. Имя, которого нет в папке, даёт
`startup_failed` с именем файла, а схема не меняется ни в одном модуле. На чистой базе проверка
ничего не создаёт.

**Откат приложения после миграций.** Откат контейнера не откатывает данные, миграций вниз нет.
Проверка сравнивает только имена и не знает, совместима ли схема. Поэтому:

- прежний образ пригоден только для возврата с выпуска без новых миграций;
- образ без нового имени не запустится даже после совместимого расширения. При совместимой схеме
  прежнее поведение возвращает новый образ: прежний код и все применённые файлы миграций, обычным
  выпуском. Это осознанная цена: для финансовых данных отказ безопаснее предположения о
  совместимости;
- при несовместимой схеме выход — исправление вперёд;
- в образах до этой проверки, в том числе M10, её нет: такой образ запустится и после новых
  миграций, поэтому после первой новой миграции его запускать нельзя.

Что делать, если применилась только часть набора, — подраздел «Частично применённый набор».
Копию восстанавливают только рядом с рабочей базой, по разделу «Восстановление из копии».

## Установка

Сертификат выпускается до первого запуска, пока порт 80 свободен, а хуки продления привязываются,
когда nginx уже работает. В командах `hof.example.org` заменяют своим доменом.

1. **DNS и порты.** У домена только A-запись на IPv4 сервера. CAA-записи, если они есть у домена
   или родительского домена, должны разрешать `letsencrypt.org`. Порты 80 и 443 на сервере
   свободны:

   ```sh
   dig +short A hof.example.org @1.1.1.1     # IPv4 сервера
   dig +short AAAA hof.example.org @1.1.1.1  # пусто
   ss -tlnp | grep -E ':(80|443) '           # пусто
   ```

   Доступность порта 80 снаружи проверяет первая команда certbot (шаг 4).

2. **Код:**

   ```sh
   git clone https://github.com/vrubovoy/hof.git /opt/hof
   cd /opt/hof
   git checkout <тег>
   stat -c '%a %n' deploy/postgres-init.sh   # 755
   ```

   Если права не `755`, а `700` или `600` (клон сделан при `umask 077`), до первого запуска
   выполняют `chmod a+rx deploy/postgres-init.sh`. Иначе PostgreSQL не сможет выполнить скрипт:
   инициализация упадёт, контейнер перезапустится и второй раз её пропустит — останется база `hof`
   без ролей и схем Hof, хотя `pg_isready` ответит, что сервер готов.

3. **`.env`.** Пароли создаются на месте и на экран не выводятся:

   ```sh
   (umask 077; {
     echo "POSTGRES_PASSWORD=$(openssl rand -hex 24)"
     echo "HOF_CORE_DB_PASSWORD=$(openssl rand -hex 24)"
     echo "HOF_SAECKEL_DB_PASSWORD=$(openssl rand -hex 24)"
     echo "CURRENCY=RUB"
     echo "TZ=Europe/Moscow"
     echo "HOF_DOMAIN=hof.example.org"
   } > .env)
   chmod 600 .env
   ```

   Что значат `CURRENCY` и `TZ` — в `.env.example`. Валюту фиксирует первая запись Säckel, потом
   её не сменить. На сервере с соседними сервисами добавляют строку `COMPOSE_FILE` (раздел
   «Маломощный сервер с соседними сервисами»). `.env` в Git не попадает.

4. **Сертификат** — certbot из пакетов дистрибутива: сначала проверка на тестовом сервере Let's
   Encrypt, затем настоящий сертификат. Обе команды — без хуков: стек ещё не запущен.

   ```sh
   apt install certbot
   certbot certonly --standalone --dry-run --cert-name hof.example.org -d hof.example.org \
     --non-interactive --agree-tos --register-unsafely-without-email
   certbot certonly --standalone --cert-name hof.example.org -d hof.example.org \
     --non-interactive --agree-tos --register-unsafely-without-email
   install -m 755 -o root -g root deploy/certbot-hook.sh /usr/local/sbin/hof-certbot-hook
   ```

   Первая команда проверяет DNS, CAA и доступность порта 80 извне: «The dry run was successful».
   `--agree-tos` — согласие с условиями Let's Encrypt. Адрес почты не нужен: писем об истечении
   Let's Encrypt не присылает. Пакет certbot сам включает `certbot.timer`.

5. **Запуск:**

   ```sh
   docker compose up -d --build
   docker compose ps
   docker compose logs hof
   ```

   В логе `hof` — `info start … migrations=core/001_users.sql,…` и `info gate_key key=…`. Затем
   проверяют, что PostgreSQL создал роли и схемы, — `pg_isready` этого не показывает:

   ```sh
   docker compose exec -T postgres psql --username=postgres --dbname=hof -At \
     -c "SELECT string_agg(rolname, ',' ORDER BY rolname) FROM pg_roles WHERE rolname LIKE 'hof%'" \
     -c "SELECT string_agg(nspname || ':' || pg_get_userbyid(nspowner), ',' ORDER BY nspname) FROM pg_namespace WHERE nspname IN ('core', 'saeckel')"
   ```

   Должно быть `hof_core,hof_saeckel` и `core:hof_core,saeckel:hof_saeckel`. Если ролей нет, том
   инициализирован неверно (шаг 2). Том при этом не трогают и решение принимает владелец; очистка
   возможна только при условиях раздела «Очистка временной установки».

6. **nginx отдаёт выпущенный сертификат** — серийные номера совпадают:

   ```sh
   echo | openssl s_client -connect hof.example.org:443 -servername hof.example.org 2>/dev/null | openssl x509 -noout -serial
   openssl x509 -in /etc/letsencrypt/live/hof.example.org/cert.pem -noout -serial
   ```

7. **Хуки продления** — только для этого сертификата:

   ```sh
   certbot reconfigure --cert-name hof.example.org \
     --pre-hook "/usr/local/sbin/hof-certbot-hook pre" --post-hook "/usr/local/sbin/hof-certbot-hook post"
   ```

   `reconfigure` сам делает пробное продление на тестовом сервере: в выводе
   `hof-certbot-hook: nginx … остановлен`, затем `… запущен` и «Successfully updated
   configuration». Хуки записываются в `/etc/letsencrypt/renewal/hof.example.org.conf`; каталог
   `renewal-hooks/` не используется, поэтому другие сертификаты хоста этих хуков не получат.

8. **Основание двора.** Ключ от ворот — последняя строка `info gate_key`:

   ```sh
   docker compose logs hof | grep 'info gate_key' | tail -1
   ```

   Ключ действует до основания двора или до перезапуска `hof`: каждый запуск печатает новый. В
   браузере открывают `https://hof.example.org/`, вводят ключ, логин и пароль Хозяина (не короче 15
   символов) и попадают на Двор. Приближённых Хозяин принимает в «Приближённых»: логин и начальный
   пароль, который сам передаёт человеку.

## Очистка временной установки

Только для установки, которая заведомо временная и никогда не вводилась в эксплуатацию. Проект `hof`
и пустая таблица `users` этого не доказывают. Обязательны все условия:

1. Сервер и каталог установки проверены как временные: это не сервер двора, каталог создан для этой
   проверки (`hostname`, `pwd`).
2. Том принадлежит проекту этой установки, его не используют другие контейнеры. Первая команда
   выводит имя проекта, вторая — только контейнеры этого проекта:

   ```sh
   docker volume inspect --format '{{ index .Labels "com.docker.compose.project" }}' <проект>_pgdata
   docker ps --all --filter volume=<проект>_pgdata --format '{{.Names}}'
   ```

3. Исполнитель подтверждает, что это не production.
4. Том удаляют по точному имени, без `prune`:

   ```sh
   docker compose down
   docker volume rm <проект>_pgdata
   ```

## Маломощный сервер с соседними сервисами

`deploy/compose.limits.yaml` ограничивает память контейнеров на сервере, где Hof делит небольшую
память с другими сервисами. В стандартную установку он не входит: `compose.yaml` лимитов не задаёт.
Файл действует, только если в `.env` этого сервера есть строка

```
COMPOSE_FILE=compose.yaml:deploy/compose.limits.yaml
```

и `docker compose` запускается из каталога Hof. Проверить, что лимиты применились:
`docker compose config` показывает `mem_limit` и `memswap_limit`, а
`docker inspect --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}' <контейнер>` — два
одинаковых числа.

`memswap_limit` равен `mem_limit`, поэтому контейнер не получает swap; swap самого сервера не
меняется. Если контейнер упирается в лимит, ядро завершает процесс только внутри него: сервер Hof
Docker перезапускает вместе с контейнером, а потерянный процесс PostgreSQL база восстанавливает
сама. Это снижает риск, что Hof помешает соседним сервисам, но не гарантирует им память: сборка
образа, кэш файлов, ядро и сами соседи лимитами не ограничены. Значения — замеренный пик каждого
контейнера с запасом; в лимит `hof` входит и `docker compose exec hof node src/cli.ts`, потому что
команда работает в том же контейнере.

Лимиты на сервере проверяют и в cgroup: у каждого контейнера Hof `memory.max` — его лимит, а
`memory.swap.max` — `0`.

```sh
for c in hof-postgres-1 hof-hof-1 hof-nginx-1; do cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' $c).scope/memory.{max,swap.max} | paste -sd' '; done
```

Лимиты — PostgreSQL 128 MiB, Hof 256 MiB, nginx 64 MiB, всего 448 MiB. PostgreSQL доходит до
своего лимита кэшем файлов: ядро вытесняет кэш внутри лимита, OOM при этом нет. Своей памяти у
PostgreSQL 5–14 MiB, общей — 20 MiB при базе 8 МБ; `shared_buffers` по умолчанию — 128 MB, поэтому
когда база приблизится к этому размеру, лимит пересматривают.

Пороги на таком сервере. Во время загрузки образов и сборки во второй SSH-сессии смотрят
`vmstat -S M 1`; память — столбец `available` в `free -m`.

- Перед сборкой: available не меньше 400 MiB, в swap меньше 100 MiB, на `/` свободно не меньше
  3 ГБ.
- Во время загрузки образов и сборки: available ниже 150 MiB или `si` не возвращается к нулю —
  сборку прерывают, Ctrl+C безопасен.
- После запуска и 10 минут простоя: available не меньше 250 MiB, `si` и `so` — 0.
- После работы: available не меньше 150 MiB, OOM нет (`journalctl -k | grep -i oom`,
  `docker inspect -f '{{.State.OOMKilled}}' <контейнер>`), на `/` свободно не меньше 1,5 ГБ.

Порог не выполнен — `docker compose stop` и сервер больше: 2 ГБ памяти, 20–25 ГБ диска. Пороги —
контрольные точки, а не гарантия, что между замерами памяти хватит.

Замеры на сервере с 1 vCPU, 961 MiB и тремя VPN-контейнерами (2026-10-19). До установки: available
537 MiB, в swap 45 MiB, на `/` свободно 3,8 ГБ. Наименьшее available: при загрузке образов —
491 MiB, при сборке — 439 MiB, при запуске — 465 MiB, после 600 запросов — 440 MiB. Через 50 минут
простоя — 456 MiB, `si` и `so` — 0, в swap 94 MiB: ядро вынесло туда неактивные страницы во время
сборки. OOM нет; после установки на `/` свободно 2,7 ГБ.

## Сертификат

- `certbot.timer` дважды в сутки запускает `certbot -q renew --no-random-sleep-on-renew`. Пока до
  конца срока больше 30 дней, ничего не происходит и хуки не запускаются. Когда срок подошёл:
  pre-hook останавливает nginx Hof, только если тот работал, и оставляет флаг
  `/run/hof-certbot-nginx-hof`; certbot занимает порт 80 и проходит проверку; новые файлы ложатся в
  `archive/`, ссылки в `live/` обновляются; post-hook запускает nginx, только если его остановил
  pre, и nginx при старте читает новый сертификат. Сайт недоступен несколько секунд — при пробном
  продлении 7 с.
- Хук находит nginx по меткам Compose (проект `hof`, сервис `nginx`) и вызывает `/usr/bin/docker`
  напрямую. `/opt/hof`, `.env` и `COMPOSE_FILE` ему не нужны, поэтому он работает и посреди
  обновления. Намеренно остановленный nginx хук не запускает.
- Проверка продления без нового сертификата:

  ```sh
  certbot renew --dry-run --cert-name hof.example.org
  ```

  Успех — «Congratulations, all simulated renewals succeeded». Работавший nginx перезапущен
  (`docker inspect -f '{{.State.StartedAt}}' hof-nginx-1`), флага в `/run` нет, серийный номер
  сертификата прежний; остановленный nginx так и остаётся остановленным. Без терминала (из скрипта
  по ssh) команда сначала ждёт случайное время, до нескольких минут.

- Раз в месяц: `certbot certificates` — срок, `journalctl -u certbot` — ошибки продления.
- После первого настоящего продления (примерно через 60 дней) дата окончания в
  `certbot certificates` совпадает с той, что отдаёт nginx:

  ```sh
  echo | openssl s_client -connect hof.example.org:443 -servername hof.example.org 2>/dev/null | openssl x509 -noout -enddate
  ```

- Сбои продления:
  - проверка или pre-hook не удались — post запускает nginx со старым сертификатом, если тот был
    остановлен; certbot повторит через 12 часов, запас — около 30 дней;
  - post-hook не смог запустить nginx — сайт недоступен, флаг остаётся (раздел «Диагностика»);
  - перезагрузка между pre и post — nginx остаётся остановленным: `docker compose start nginx`.
- `--force-renewal` не используют: пробное продление проверяет хуки, порт 80 и ACME-проверку, а
  настоящее расходует лимит Let's Encrypt.

## Контейнеры и логи

```sh
docker compose ps                         # что работает
docker compose logs --since 10m hof nginx # логи за 10 минут
docker compose stop                       # остановить; контейнеры и данные остаются
docker compose start                      # запустить остановленные снова
docker compose restart hof                # перезапустить Hof; nginx перезапускается вместе с ним
```

`docker compose down` удаляет контейнеры, том с данными остаётся. `docker compose down -v` удаляет
и том `hof_pgdata` со всеми записями: на действующей установке она запрещена (раздел «Правила
сохранности данных»).

Контейнеры поднимаются сами (`restart: unless-stopped`) после падения процесса и после перезапуска
Docker, но не после `docker compose stop`. `hof` останавливается сразу: первым процессом в
контейнере работает init Docker (`init: true`), он передаёт SIGTERM в Node. Docker хранит логи
каждого контейнера в трёх файлах по 10 МБ, старые строки уходят. Access log nginx пишется без query
и Referer; что пишет Hof — ARCHITECTURE.md §4.10.

У `hof` есть healthcheck: раз в 30 секунд Docker запрашивает `/healthz` прямо на порту Hof внутри
контейнера, без nginx. `docker compose ps` показывает статус:

- `health: starting` — первые секунды после запуска;
- `healthy` — процесс принимает запросы. У только что запущенного контейнера это значит и успешный
  старт: порт открывается после подключения к базе и миграций;
- `unhealthy` — три проверки подряд не получили ответ 200 за 3 секунды (пункт «Диагностика»).

Это проверка процесса, а не базы: если PostgreSQL перестал отвечать уже после старта, статус
остаётся `healthy`. По статусу ничего не перезапускается. Адрес `/healthz` доступен и снаружи, через
nginx, и отвечает только `ok`.

## Восстановление доступа

Пароль приближённого сбрасывает Хозяин: «Приближённые» → «Открыть ›» → «Сбросить пароль».
Если пароль забыл сам Хозяин, новый задают на сервере:

```sh
docker compose exec hof node src/cli.ts reset-password <логин>
```

Команда спрашивает новый пароль дважды; набранное на экране не видно. Правила те же, что в
форме: не короче 15 символов, повтор должен совпасть. После сброса все сессии этого человека
завершаются, войти можно только с новым паролем. Отключённый пользователь остаётся отключённым.

Пароль вводится только с клавиатуры: аргументом, через переменную окружения или из перенаправленного
ввода (`< файл`, `|`, `docker compose exec -T`) команда его не примет и откажется работать. Ctrl+C
отменяет сброс, ничего не меняя. Строка `info password_reset` печатается в этом же терминале, в
`docker compose logs` её нет: команда — отдельный процесс.

## Резервная копия

Копия — один файл формата custom от `pg_dump` со всей базой `hof`: схемы `core` и `saeckel` с
владельцами, таблицы, данные, индексы и обе таблицы `schema_migrations`. Ролей и их паролей в копии
нет: на новом томе их создаёт `deploy/postgres-init.sh` из `.env`. Зато в копии есть хеши паролей и
все бюджеты, поэтому файл хранят как секрет: права 600, вне каталога Hof (иначе он попадёт в
контекст сборки образа), не в Git и не в облаке.

Команды выполняются в каталоге Hof, где лежат `compose.yaml` и `.env`. Hof останавливать не нужно:
`pg_dump` читает согласованный снимок базы. Пароль суперпользователя тоже не нужен: `pg_dump`
работает внутри контейнера `postgres` через локальный сокет.

```sh
mkdir -p ~/hof-backups && chmod 700 ~/hof-backups
f=~/hof-backups/hof-$(date +%Y-%m-%d-%H%M%S)-$(git rev-parse --short HEAD).dump
part=$(mktemp "$f.part.XXXXXX")
docker compose exec -T postgres pg_dump --username=postgres --dbname=hof --format=custom > "$part" \
  && docker compose exec -T postgres pg_restore --list < "$part" > /dev/null \
  && ln "$part" "$f" && rm -f "$part" && echo "Копия готова: $f" \
  || { rm -f "$part"; echo "Копия НЕ сделана"; false; }
```

Пока `pg_dump` пишет, файл называется `….dump.part.XXXXXX`: `mktemp` даёт каждому запуску своё имя,
поэтому у двух одновременных копий временные файлы разные. Имя `.dump` появляется, только если
`pg_dump` завершился с кодом 0 и `pg_restore --list` прочитал оглавление архива; иначе временный
файл удаляется, а команда завершается с ошибкой. `ln` создаёт имя `.dump`, только если такого файла
ещё нет, поэтому готовую копию команда никогда не заменяет: вторая копия в ту же секунду получает
`File exists` и «Копия НЕ сделана», её просто запускают ещё раз. В имени — дата, время и коммит
кода, с которым сделана копия: восстанавливают её с кодом этого же коммита (раздел «Восстановление
из копии»).

Права задают сами команды: каталог закрывает `chmod 700`, а файл `mktemp` создаёт с правами 600,
и `ln` их сохраняет. `umask` сеанса команды не меняют, чтобы следующий `git checkout` в том же терминале не создал
файлы с правами 600.

Читаемый архив ещё не доказывает, что из него поднимется двор. Это проверяют учения (раздел
«Проверить копию»).

### Перенести копию на свой компьютер

Копия на том же сервере пропадёт вместе с ним, а места на небольшом сервере мало. Поэтому копию
сразу переносят к себе, сверяют контрольную сумму и на сервере оставляют только последние. На своём
компьютере:

```sh
mkdir -p ~/hof-backups && chmod 700 ~/hof-backups
scp <сервер>:hof-backups/<файл>.dump ~/hof-backups/
shasum -a 256 ~/hof-backups/<файл>.dump
ls -l ~/hof-backups/<файл>.dump
```

На сервере та же сумма — `sha256sum ~/hof-backups/<файл>.dump`; суммы должны совпасть. `ls -l`
показывает `-rw-------`. Старые копии на сервере удаляют по имени:
`rm ~/hof-backups/<старый файл>.dump`.

## Автоматические копии

Ночная копия создаётся без участия человека, а Mac забирает её с сервера. Установка на сервер
выполняется только по отдельному решению владельца. Команды выполняются от root, если не сказано
иное.

### Как устроено

- **Копия.** `hof-backup` находит контейнер `postgres` по меткам Compose, как `certbot-hook`, и
  запускает `pg_dump`: это согласованный снимок, Hof не останавливают. Архив читается целиком
  (`pg_restore --file=/dev/null`), затем считается SHA-256. Рабочее имя файл получает только после
  этого; `.part` при сбое удаляется. Рядом с архивом лежит `.meta`: время, размер, SHA-256, образ
  Hof.
- **Каталог** `/var/backups/hof`: `root:hof-backup`, права `2750`, файлы `640`. Итог последней
  попытки — в `backup-status.txt`: `OK` или `FAIL` с причиной. Там же видно, что копию не удалось
  создать.
- **Расписание.** `hof-backup.timer` запускает копию в 03:30 по времени сервера. После простоя
  сервера пропущенный запуск выполняется через две минуты после загрузки, когда поднимутся
  контейнеры.
- **Хранение на сервере.** 7 последних ночных и 3 последние предрелизные копии, по количеству, а не
  по возрасту. Очистка идёт только после новой проверенной копии и только среди файлов того же вида
  с именем по шаблону. Ручные копии не затрагиваются.
- **Место.** Перед копией нужно свободно 1,5 ГБ плюс двойной размер прошлой копии. Если места нет:
  ошибка, `FAIL`, все прежние копии остаются. Исправные копии ради новой попытки не удаляются: место
  освобождает человек.
- **Блокировка.** Копии и обновление используют один `flock` на `/run/lock/hof-ops.lock`. Ночной
  запуск ждёт до 10 минут, ручной — до 60 секунд. Дольше занято: сообщение с последней записью в
  файле блокировки, выход с кодом 3, файлы не меняются. Блокировка освобождается сама при завершении
  процесса. Команда обновления держит блокировку сама и вызывает копию с `--lock-held`; через SSH
  этот флаг недоступен.

Замер на ноутбуке arm64, лимит контейнера 128 MiB, база 131 МБ и 500 000 строк: копия 1 с, пик
памяти контейнера 36 МиБ, OOM нет. На реальных данных сервера замер повторяют при установке.

### Установка на сервер

До установки проверяют, что sshd пустит нового пользователя: `sshd -T | grep -iE 'allowusers|allowgroups'`
ничего не выводит. Если выводит, настройки sshd меняют только с отдельного разрешения.

Файлы копируют с компьютера: рабочую копию `/opt/hof` это не меняет.

```sh
ssh <сервер> mkdir -p /tmp/hof-backup-install
scp deploy/hof-backup.sh deploy/hof-backup-send.sh deploy/hof-backup.service deploy/hof-backup.timer <сервер>:/tmp/hof-backup-install/
```

На сервере:

```sh
cd /tmp/hof-backup-install
useradd --system --home-dir /var/lib/hof-backup --no-create-home --shell /bin/sh hof-backup
usermod --password '*' hof-backup
install -d -m 755 /var/lib/hof-backup /var/lib/hof-backup/.ssh
install -d -m 700 -o hof-backup -g hof-backup /var/lib/hof-backup/state
install -d -m 2750 -g hof-backup /var/backups/hof
install -m 755 hof-backup.sh /usr/local/sbin/hof-backup
install -m 755 hof-backup-send.sh /usr/local/sbin/hof-backup-send
install -m 644 hof-backup.service hof-backup.timer /etc/systemd/system/
systemctl daemon-reload
hof-backup
systemctl enable --now hof-backup.timer
systemctl list-timers hof-backup.timer
```

`hof-backup` без аргументов выводит «копия готова» с именем и размером. Пользователь `hof-backup`
входит только по ключу: вместо пароля `*`. Каталоги `/var/lib/hof-backup` и `.ssh` принадлежат root,
поэтому ключ не может изменить свой `authorized_keys`; пользователь может писать только в `state/`,
где лежит время последнего забора. Он вне групп `docker` и `sudo`.

### Копия на Mac

Ключ создаётся только для забора копий и больше нигде не используется. Пароля у него нет, потому что
launchd запускает забор без участия человека; даёт он только чтение копий.

```sh
ssh-keygen -t ed25519 -N '' -C hof-backup-mac -f ~/.ssh/hof_backup_ed25519
cat ~/.ssh/hof_backup_ed25519.pub
```

На сервере, с содержимым `.pub` вместо `<ключ>`. `restrict` запрещает терминал и пробросы, `command`
оставляет единственную команду: `list`, `fetch <имя>` или `status`.

```sh
printf 'restrict,command="/usr/local/sbin/hof-backup-send" %s\n' '<ключ>' > /var/lib/hof-backup/.ssh/authorized_keys
chmod 644 /var/lib/hof-backup/.ssh/authorized_keys
```

На Mac в `~/.ssh/config`:

```
Host hof-backup
  HostName <адрес сервера>
  User hof-backup
  IdentityFile ~/.ssh/hof_backup_ed25519
  IdentitiesOnly yes
```

Первое подключение запоминает ключ сервера; дальше скрипт принимает только его. Затем установка и
первый запуск, из каталога репозитория:

```sh
ssh -o StrictHostKeyChecking=accept-new hof-backup list
fdesetup status
mkdir -p ~/.local/bin ~/Library/LaunchAgents
install -m 755 deploy/hof-backup-pull.sh ~/.local/bin/hof-backup-pull
sed "s|@HOME@|$HOME|g" deploy/hof-backup-pull.plist > ~/Library/LaunchAgents/hof.backup-pull.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/hof.backup-pull.plist
tail ~/Library/Logs/hof-backup-pull.log
```

launchd запускает забор при загрузке и каждый час, пока Mac не спит. Забираются все недостающие
копии, которые ещё есть на сервере: файл `.part`, сверка SHA-256, переименование. Повтор после сбоя
— следующий часовой запуск.

Копия считается полной, если у архива есть `.meta` с SHA-256 и размер совпадает с записанным.
Неполная копия, которая ещё есть на сервере, забирается заново и заменяется только после сверки
SHA-256. Если забрать её нельзя, файл остаётся на месте, приходит уведомление, а для возраста копий
он не считается.

Хранение на Mac: 30 последних ночных, по одной за месяц за 12 месяцев, 5 предрелизных. Очистка идёт
только после новой проверенной копии, по количеству, поэтому долгий простой историю не удаляет.
Ручные копии в том же каталоге не затрагиваются.

**Защита данных.** В копиях бюджеты и хеши паролей, поэтому:

- FileVault обязателен: при выключенном скрипт предупреждает и не забирает копии;
- `~/hof-backups` имеет права 700, файлы — 600, каталог закрыт от Spotlight и не должен оказаться в
  iCloud Drive;
- каталог исключён из Time Machine: если `tmutil addexclusion` завершился ошибкой, скрипт
  предупреждает и не забирает копии. Причина — в логе. Забирать копии без исключения можно только по
  отдельному решению владельца: `touch ~/hof-backups/.time-machine-allowed`;
- в логе и уведомлениях только имена, размеры и возраст; ответ сервера в текст уведомления не
  попадает;
- при потере Mac на сервере удаляют строку ключа из `authorized_keys` и меняют пароли Хозяина и
  приближённых.

### Пропуски и их пределы

Уведомление на Mac приходит не чаще раза в 12 часов по каждому поводу:

| Сигнал                                                           | Что значит                                               |
| ---------------------------------------------------------------- | -------------------------------------------------------- |
| «На сервере нет копии моложе 36 часов»                           | Timer не работает или копии не создаются                 |
| «Последняя копия на сервере не создана»                          | В `backup-status.txt` стоит `FAIL`; причина в логе Mac   |
| «На Mac нет копии моложе 36 часов»                               | Забор не проходит                                        |
| «Сервер недоступен больше суток»                                 | Нет связи с сервером                                     |
| «…возможен разрыв»                                               | Самая старая ночная копия на сервере новее локальной     |
| «Копия с сервера не совпала по SHA-256»                          | Файл испорчен при передаче и не сохранён                 |
| «FileVault выключен: копии не забираются»                        | Включить FileVault                                       |
| «Каталог копий не исключён из Time Machine: копии не забираются» | Причина в логе; настроить исключение или принять решение |
| «Есть копия без проверяемых сведений…»                           | Архив сохранён, но не считается полным; имена в логе     |

Ограничения:

- **Окно потерь не обещается.** Измеряются две величины: возраст новейшей копии на сервере (при
  потере базы) и на Mac (при потере сервера). Посмотреть их можно командой `ssh hof-backup list` и
  `ls ~/hof-backups`.
- **Выключенный Mac уведомить не может.** Сигнал придёт после включения.
- **Уведомление не показано.** Ошибка остаётся в логе, а следующий запуск пробует снова.
- **Содержимое архивов каждый час не перечитывается.** Порчу при том же размере находит сверка
  SHA-256 при восстановлении, а не часовой запуск.
- **Удалённое не вернуть.** Mac, не работавший дольше срока хранения на сервере, не получит уже
  удалённые архивы: в истории на Mac останется разрыв. Новейшая копия при этом всё равно забирается.
- **Занятая блокировка** может отменить одну ночную копию; она проявится как возраст копии.

## Проверить копию

Учения: `deploy/hof-restore-check.sh` восстанавливает копию на этом компьютере в отдельный временный
проект Compose и запускает на ней Hof. К серверу скрипт не обращается, с рабочей базой копию не
сравнивает.

```sh
deploy/hof-restore-check.sh ~/hof-backups/<файл>.dump
```

Нужны локальный Docker и этот же репозиторий: образ Hof собирается из него. Рядом с архивом должен
лежать `.meta` с SHA-256, как у автоматических копий. У ручной копии его можно создать, сверив сумму
с сервером: `printf 'sha256=%s\n' <сумма> > <файл>.dump.meta`.

Правило: учения проводят раз в месяц и перед каждым выпуском с миграциями. Если код новее копии, Hof
применит его миграции к временной базе и отчёт их назовёт: это репетиция обновления на реальных
данных. Для восстановления на сервере так нельзя (раздел «Восстановление из копии»). Если копия новее
кода, Hof откажется стартовать и назовёт неизвестные миграции, скрипт завершится с кодом 1: такую
копию проверяют кодом, который знает её миграции.

Скрипт останавливается на первой ошибке и всегда убирает за собой:

1. Сверяет SHA-256 с `.meta`, ещё до запуска контейнеров.
2. Поднимает `postgres` из `compose.yaml` в проекте `hof-drill-<случайное>` с новыми случайными
   паролями. Это заодно доказывает, что копии не нужны старые секреты.
3. Читает архив целиком (`pg_restore --file=/dev/null`).
4. Проверяет, что Docker локальный, а контейнер и том принадлежат этому проекту, и только затем
   пересоздаёт базу: `postgres-init.sh` уже создал в ней схемы, и архив на них упал бы. Роли остаются,
   схемы с владельцами приносит архив. Восстановление идёт одной транзакцией, поэтому при ошибке
   частичных данных не остаётся.
5. Проверяет структуру: схемы и таблицы с владельцами `hof_core` и `hof_saeckel`, первичные ключи, два
   внешних ключа `operations`, индекс `users_one_admin`, отсутствие непроверенных ограничений.
6. Проверяет записи: ровно один Хозяин и одна валюта.
7. Собирает образ и запускает Hof: должна быть строка `info start`, не должно быть `gate_key` и
   `startup_failed`.

Отчёт содержит имя файла, число записей, дату новейшей операции, отпечаток записей и миграции. Имён и
сумм в нём нет. Сверять число записей с ожидаемым должен человек: с живой базой скрипт копию намеренно
не сравнивает, потому что записи меняются и после снимка. Отпечаток — это хеш всех записей: у копий с
одними и теми же данными он совпадает, хотя SHA-256 архивов разные, потому что в архиве есть время
создания.

Код выхода: 0 — копия прошла проверку; 1 — не прошла или проверка не удалась; 2 — неверный аргумент или
Docker не локальный, тогда ничего не запускалось. Контекст Docker или `DOCKER_HOST` с адресом вроде
`ssh://` скрипт отклоняет: так он не попадёт на сервер.

Другие контейнеры Hof на компьютере не мешают и не затрагиваются, несколько проверок могут идти
одновременно: порты не публикуются, а у каждого прогона свои контейнеры, сеть, том и образ. Очистка
удаляет только их, по точным именам, и затем проверяет, что их больше нет. Если подтвердить это нельзя,
например Docker перестал отвечать, скрипт завершается с кодом 1 и называет проект, даже если сама копия
прошла проверку. В томе на этом компьютере тогда могут оставаться данные копии. То же после убитого
процесса. Найти и удалить их:

```sh
docker ps -a --filter name=hof-drill- --format '{{.Names}}'
docker volume ls --filter name=hof-drill- --format '{{.Name}}'
docker rm -f hof-drill-<случайное>-hof-1 hof-drill-<случайное>-postgres-1
docker network rm hof-drill-<случайное>_default
docker volume rm hof-drill-<случайное>_pgdata
docker image rm hof-drill-<случайное>-hof
```

## Восстановление из копии

Ручная процедура, только по отдельному решению владельца. Копия разворачивается в соседнюю базу
`hof_restore`, и только после проверки базы меняются именами. Рабочая база не удаляется и не
перезаписывается: она остаётся рядом как `hof_before_restore`, и пока с новой базой никто не работал,
к ней можно вернуться (шаг 19). **Всё, что записали после создания копии, в новой базе `hof`
отсутствует** и остаётся только в `hof_before_restore`.

Команды выполняются от root в каталоге Hof одним сеансом терминала: в нём живут блокировка, функция
`props`, переменная `copy` и отметки `lock_ok`, `space_ok`, `copy_ok`. Отметку ставит только успешный
шаг 1, 2 или 3. Блоки, которые останавливают Hof, создают `hof_restore`, восстанавливают в неё копию
или меняют имена баз, без нужных отметок ничего не делают и печатают «СТОП». `exit` и `set -e` не
используются: они закрыли бы терминал и сняли блокировку.

Если сеанс оборвался, блокировка снята, а отметки пропали. В новом сеансе снова выполняют шаги 1–3 и
задают `props`. Если имена баз уже поменялись (шаг 15), для обратного переключения достаточно шага 1.

### Подготовка

1. Записать причину решения и взять блокировку. Её удерживают на всё время процедуры. Если она занята,
   блок печатает «СТОП» и того, кто её держит; дожидаются конца той операции и повторяют блок:

   ```sh
   lock_ok= space_ok= copy_ok=
   echo "$(date '+%F %T') восстановление: <причина и решение владельца>" >> ~/hof-backups/updates.log
   exec 9>>/run/lock/hof-ops.lock
   if flock --nonblock 9; then
     : >/run/lock/hof-ops.lock
     echo "восстановление, с $(date -u +%FT%TZ)" >&9
     lock_ok=yes
     echo 'Блокировка взята'
   else
     echo "СТОП: блокировка занята: $(cat /run/lock/hof-ops.lock)"
   fi
   ```

   Затем остановить таймеры и Hof и посмотреть имена баз. Должна быть только база `hof`; база от
   прошлого восстановления удаляется только решением владельца (шаг 22).

   ```sh
   if [ "$lock_ok" = yes ]; then
     systemctl stop hof-backup.timer
     systemctl stop hof-check.timer     # если установлен
     docker compose stop hof
     docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc -At \
       -c "SELECT datname FROM pg_database WHERE datname LIKE 'hof%' ORDER BY 1"
   else
     echo 'СТОП: блокировка не взята'
   fi
   ```

2. Свободно не меньше двойного размера текущей базы плюс 1,5 ГБ. Если места мало или размер базы либо
   свободное место не получены, `space_ok` не ставится:

   ```sh
   space_ok=
   size=$(docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc -At --set ON_ERROR_STOP=1 -c "SELECT pg_database_size('hof')")
   free=$(df --output=avail -B1 "$(docker info --format '{{.DockerRootDir}}')" | tail -n 1 | tr -d ' ')
   if [[ ! $size =~ ^[0-9]+$ || ! $free =~ ^[0-9]+$ ]]; then
     echo "СТОП: не получены размер базы или свободное место: size='$size' free='$free'"
   elif (( free < 2 * size + 1536 * 1024 * 1024 )); then
     echo "СТОП: мало места: свободно $free байт, база $size байт"
   else
     space_ok=yes
     echo "Места хватает: свободно $free байт, база $size байт"
   fi
   ```

3. Выбранная копия прошла учения (раздел «Проверить копию»). Её вместе с `.meta` сначала кладут в
   `~/hof-backups` на сервере: `cp` из `/var/backups/hof` или `scp` с Mac. Оттуда её не удалит
   очистка старых копий, в том числе в `hof-backup` ниже: он оставляет только 3 последние
   предрелизные копии. Блок сверяет SHA-256 с `.meta` и только при совпадении делает свежую копию
   текущей базы. Нет `.meta`, сумма не посчитана, не совпала или свежая копия не создана —
   `copy_ok` не ставится, а архивы и рабочая база не меняются:

   ```sh
   copy_ok=
   copy=~/hof-backups/<файл>.dump
   expected=$(sed -n 's/^sha256=//p' "$copy.meta")
   actual=$(sha256sum "$copy" | cut -d' ' -f1)
   if [ "$lock_ok$space_ok" != yesyes ]; then
     echo 'СТОП: шаги 1–2 не пройдены'
   elif [ -z "$expected" ] || [ "$expected" != "$actual" ]; then
     echo "СТОП: SHA-256 не совпала или не получена: .meta '$expected', файл '$actual'"
   elif ! hof-backup --pre-deploy --lock-held; then
     echo 'СТОП: свежая копия текущей базы не создана'
   else
     copy_ok=yes
     echo 'Сумма совпала, свежая копия создана'
   fi
   ```

   Если рабочая база не читается и свежую копию сделать нельзя, дальше идут только по отдельному
   решению владельца: его записывают в `updates.log`, а `copy_ok=yes` после совпадения суммы задают
   вручную.

   Код сервера должен знать миграции копии и не приносить новых: в отчёте учений на этом коде —
   «новые миграции этого кода: none». Если код новее копии, например после неудачного обновления,
   его возвращают: `git checkout <коммит копии>`, `docker compose build hof`.

### Создание

4. Прочитать свойства `hof` из `pg_database`: владелец, кодировка, провайдер локали, локаль. Та же
   функция выводит настройки базы и права схем для сверки:

   ```sh
   props() {
     docker compose exec -T postgres psql --username=postgres --dbname="$1" --no-psqlrc -At --set ON_ERROR_STOP=1 <<'SQL'
   SELECT 'база', pg_get_userbyid(datdba), pg_encoding_to_char(encoding), datlocprovider, datcollate, datctype,
          datlocale, daticurules, datconnlimit, coalesce(datacl, acldefault('d', datdba))
     FROM pg_database WHERE datname = current_database();
   SELECT 'настройка', coalesce(r.rolname, '(все роли)'), s.setconfig
     FROM pg_db_role_setting s LEFT JOIN pg_roles r ON r.oid = s.setrole
    WHERE s.setdatabase = (SELECT oid FROM pg_database WHERE datname = current_database())
    ORDER BY 2;
   SELECT 'схема', nspname, pg_get_userbyid(nspowner), coalesce(nspacl, acldefault('n', nspowner))
     FROM pg_namespace WHERE nspname IN ('public', 'core', 'saeckel') ORDER BY 2;
   SQL
   }
   props hof
   ```

5. Создать `hof_restore` с теми же свойствами. `template0` гарантирует чистую базу без локальных
   добавлений `template1`. Имя занято — команда завершится ошибкой. Без всех трёх отметок блок
   ничего не делает:

   ```sh
   if [ "$lock_ok$space_ok$copy_ok" = yesyesyes ]; then
   docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc --set ON_ERROR_STOP=1 <<'SQL'
   SELECT format('CREATE DATABASE hof_restore TEMPLATE template0 OWNER %I ENCODING %L LOCALE_PROVIDER %s LC_COLLATE %L LC_CTYPE %L%s',
            pg_get_userbyid(datdba), pg_encoding_to_char(encoding),
            CASE datlocprovider WHEN 'c' THEN 'libc' WHEN 'i' THEN 'icu' ELSE 'builtin' END,
            datcollate, datctype,
            CASE datlocprovider WHEN 'c' THEN '' WHEN 'i' THEN format(' ICU_LOCALE %L', datlocale)
              ELSE format(' BUILTIN_LOCALE %L', datlocale) END)
     FROM pg_database WHERE datname = 'hof'
   \gexec
   SQL
   else
     echo 'СТОП: шаги 1–3 не пройдены'
   fi
   ```

6. Восстановить копию, без `--create`, `--clean`, `--no-owner` и `--no-privileges`:

   ```sh
   if [ "$lock_ok$space_ok$copy_ok" = yesyesyes ]; then
     docker compose exec -T postgres pg_restore --username=postgres --dbname=hof_restore --single-transaction < "$copy"
   else
     echo 'СТОП: шаги 1–3 не пройдены'
   fi
   ```

   `--single-transaction` — всё или ничего, частичных данных не остаётся. Без `--no-owner`:
   владельцами должны остаться `hof_core` и `hof_saeckel`, иначе роли модулей не прочитают свои
   таблицы и не применят следующие миграции. Без `--create`: он создал бы базу под именем `hof` из
   архива, а вместе с `--clean` удалил бы рабочую. В заранее созданную базу владелец, права и
   настройки уровня базы из архива не переносятся, поэтому их сверяют вручную.

7. Сбой: удаляют только `hof_restore`, рабочая база не менялась. Затем устраняют причину и повторяют с
   шага 5 либо запускают Hof на прежней базе, как в шаге 18.

   ```sh
   docker compose exec -T postgres dropdb --username=postgres hof_restore
   ```

### Сверка

Сверяются `hof` и `hof_restore`:

8. `pg_database`: владелец, кодировка, локаль, `datacl`.
9. `pg_db_role_setting`: настройки базы и настройки ролей в этой базе.
10. Владельцы и права схем `public`, `core`, `saeckel`.

Всё это сравнивает одна команда, только если получены оба списка:

```sh
a=$(props hof) && b=$(props hof_restore) && [ -n "$a" ] && [ -n "$b" ] \
  && diff <(printf '%s\n' "$a") <(printf '%s\n' "$b") && echo 'Свойства совпадают'
```

11. Без строки «Свойства совпадают» процедура останавливается. Найденные настройки и права `hof`
    воспроизводят на `hof_restore` явно, например `ALTER DATABASE hof_restore SET …`,
    `ALTER ROLE … IN DATABASE hof_restore SET …` или `GRANT …`, и снова сверяют.
12. Роли не входят в архив и не пересоздаются: пароли и `search_path` остаются прежними.

### Проверка под ролями

13. `hof_core` читает `users`; `hof_saeckel` читает `operations` и не имеет доступа к `core.users`,
    последняя команда завершается ошибкой `permission denied for schema core`. Показатели сравнивают
    с отчётом учений.

    ```sh
    docker compose exec -T postgres psql --username=hof_core --dbname=hof_restore --no-psqlrc -At --set ON_ERROR_STOP=1 -c 'SELECT count(*) FROM users'
    docker compose exec -T postgres psql --username=hof_saeckel --dbname=hof_restore --no-psqlrc -At --set ON_ERROR_STOP=1 -c 'SELECT count(*) FROM operations'
    docker compose exec -T postgres psql --username=hof_saeckel --dbname=hof_restore --no-psqlrc -At --set ON_ERROR_STOP=1 -c 'SELECT count(*) FROM core.users'
    docker compose exec -T postgres psql --username=postgres --dbname=hof_restore --no-psqlrc <<'SQL'
    SELECT (SELECT count(*) FROM core.users)                          AS users,
           (SELECT count(*) FROM core.sessions)                       AS sessions,
           (SELECT count(*) FROM saeckel.pouches)                     AS pouches,
           (SELECT count(*) FROM saeckel.operations)                  AS operations,
           (SELECT coalesce(sum(amount), 0) FROM saeckel.operations)  AS amount;
    SELECT schemaname, tablename, tableowner FROM pg_tables
     WHERE schemaname IN ('core', 'saeckel') ORDER BY 1, 2;
    SQL
    ```

    Владельцы таблиц — `hof_core` в `core` и `hof_saeckel` в `saeckel`.

### Переключение

Команды — из базы `postgres`, с `ON_ERROR_STOP=1`.

14. Соединений с базами Hof нет: запрос возвращает 0 строк. Соединения не завершают автоматически,
    сначала выясняют их источник.

    ```sh
    docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc --set ON_ERROR_STOP=1 \
      -c "SELECT datname, pid, usename, application_name, client_addr, state FROM pg_stat_activity WHERE datname LIKE 'hof%'"
    ```

15. Поменять имена одной транзакцией, только при всех трёх отметках:

    ```sh
    if [ "$lock_ok$space_ok$copy_ok" = yesyesyes ]; then
    docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc --set ON_ERROR_STOP=1 <<'SQL'
    BEGIN;
    ALTER DATABASE hof RENAME TO hof_before_restore;
    ALTER DATABASE hof_restore RENAME TO hof;
    COMMIT;
    SQL
    else
      echo 'СТОП: шаги 1–3 не пройдены'
    fi
    ```

16. Если соединение появилось, PostgreSQL ждёт 5 с и отказывает:
    `database "hof" is being accessed by other users`. Транзакция откатывается, имена остаются.
    Возвращаются к шагу 14.
17. После любой ошибки имена сверяют по `pg_database` (последняя команда шага 1) и только потом
    выполняют следующий шаг.

### Запуск

18. Запустить Hof. Строка `info start` без `gate_key` и `startup_failed` подтверждает, что он
    подключился по сети с настоящими паролями ролей. Затем в браузере войти, открыть Мешки и Летопись.

    ```sh
    started=$(date -u +%FT%TZ)
    docker compose up -d --no-deps hof
    sleep 10
    docker compose logs --since "$started" hof
    ```

    Когда проверка прошла, снять блокировку и вернуть таймеры. Прежняя база остаётся рядом, но в
    ночные копии не входит: копируется только `hof`.

    ```sh
    exec 9>&-
    lock_ok= space_ok= copy_ok=
    systemctl start hof-backup.timer
    systemctl start hof-check.timer     # если установлен
    ```

С кодом копии Hof после восстановления не применяет ни одной миграции: в логе `migrations=none`. Если
там есть имена миграций, код новее копии, и это уже обновление. Его не смешивают с восстановлением:
сначала проверяют восстановленную базу на коде копии, потом, отдельным шагом и с новой копией перед
ним, обновляются на более новый код. Что более новый код совместим с любой старой копией, не
обещается. Если копия новее кода, Hof не стартует и называет её миграции. Если `CURRENCY` в `.env` не
совпадает с валютой записей в копии, Hof не стартует и называет обе валюты.

### Обратное переключение

19. Допустимо сразу, если Hof не стартовал или проверка не прошла и пользователи с восстановленной
    базой не работали.
20. Условия: блокировка взята (шаг 1), Hof остановлен (`docker compose stop hof`), соединений нет (шаг
    14), `hof_before_restore` на месте. Затем одной транзакцией:

    ```sh
    if [ "$lock_ok" = yes ]; then
    docker compose exec -T postgres psql --username=postgres --dbname=postgres --no-psqlrc --set ON_ERROR_STOP=1 <<'SQL'
    BEGIN;
    ALTER DATABASE hof RENAME TO hof_restore_failed;
    ALTER DATABASE hof_before_restore RENAME TO hof;
    COMMIT;
    SQL
    else
      echo 'СТОП: блокировка не взята'
    fi
    ```

    После `COMMIT` сверяют имена (шаг 17), запускают Hof, снимают блокировку и возвращают таймеры, как
    в шаге 18.

21. Если на восстановленной базе уже есть новые записи, обратное переключение их потеряет: нужны
    свежая копия, сравнение и отдельное решение владельца.
22. `hof_before_restore` и `hof_restore_failed` удаляют только отдельной ручной командой после решения
    владельца, по одному точному имени:

    ```sh
    docker compose exec -T postgres dropdb --username=postgres <имя>
    ```

Процедура проверена на временном стенде с искусственными данными: успех, упавший `pg_restore`,
отличие свойств, активное соединение (отказ через 5 с), обратное переключение. Таймеры, блокировка и
`hof-backup` на стенде заменялись заглушками. Отказы шагов 1–3 проверены отдельно в контейнере Linux
с настоящими `flock`, `df`, `sha256sum` и `hof-backup`: блокировка занята, мало места, размер базы или
свободное место не получены, сумма не совпала, нет `.meta` или архива, свежая копия не создана. Во
всех случаях Hof не останавливался или блоки создания, восстановления и переключения ничего не
делали, архивы не менялись. На сервере процедура не выполнялась.

## Обновление

Обновляются только на проверенный тег: тег milestone или корректирующий тег вроде `m7-fix.1` — его
выпускают сразу, как только исправлен дефект, не дожидаясь следующего milestone. От остановки Hof до
запуска новой версии сайт недоступен и `nginx` отвечает 502: это ожидаемый простой, а не повод
восстанавливать базу. Длительность зависит от сервера; на одном vCPU сборка образа заметно дольше,
чем на ноутбуке. Hof на время сборки остановлен и не спорит с ней за память, но процессор и память
нужны и соседним сервисам сервера, поэтому обновляются в спокойное время. На время обновления нужно
место под новый образ, кэш сборки и копию: перед началом смотрят `df -h /` и `docker system df`.

Команды выполняются в каталоге Hof одним сеансом терминала: переменные `old`, `new`, `f` и
`oldimage` нужны и в разделе «Если обновление не удалось».

1. Текущий и новый тег, что изменилось:

   ```sh
   old=$(git describe --tags --exact-match) && echo "Сейчас: $old"
   git fetch --tags
   new=<новый тег>
   git diff --stat "$old" "$new" -- src/core/migrations src/saeckel/migrations compose.yaml deploy .env.example
   ```

   Новые файлы в `migrations/` — новые миграции: сначала выполняют условия раздела «Правила
   сохранности данных», а прежний образ после них не запустится. Если изменился `.env.example`, новые переменные дописывают в `.env` до запуска. Если
   `git describe` не нашёл тег, сервер работает не на теге — сначала выясняют, на каком коммите.

2. Остановить Hof и сделать копию:

   ```sh
   docker compose stop hof
   ```

   Затем — команды раздела «Резервная копия». Без строки «Копия готова» обновление не продолжают.
   В имени копии (`echo "$f"`) стоит коммит текущего кода — тот же, что `git rev-parse --short HEAD`.

3. Запомнить образ и обновиться:

   ```sh
   oldimage=$(docker compose images -q hof)
   git checkout "$new"
   docker compose up -d --build
   docker compose ps
   docker compose logs --since 10m hof nginx
   ```

   Через несколько секунд в логе `hof` — строка `info start … migrations=…` с новыми миграциями
   через запятую или `none`, если их нет. Затем в браузере входят и открывают Мешки и Летопись.
   Звук: nginx пропускает диапазоны к static, иначе Safari не играет звуки, а музыка не
   продолжается с места:

   ```sh
   curl -s -o /dev/null -D - -H 'Range: bytes=0-1' https://hof.example.org/static/sounds/coins-1.m4a | grep -iE '^HTTP|^content-range'
   ```

   Должно быть `HTTP/2 206` и `content-range: bytes 0-1/11616`.

4. Записать результат:

   ```sh
   echo "$(date '+%F %T') $old -> $new, копия $f" >> ~/hof-backups/updates.log
   ```

### Освободить место

Когда новая версия проверена, старый образ Hof больше не нужен. Удаляют только его, по ID:

```sh
docker ps -a --filter ancestor="$oldimage" --format '{{.Names}}'
docker image rm "$oldimage"
```

Первая команда ничего не выводит, если образ не используется ни одним контейнером; иначе образ не
удаляют. Ответ `No such image` значит, что Docker уже удалил старый образ сам, когда тег перешёл на
новый: так работает хранилище образов containerd, удалять нечего. `docker system prune`,
`docker image prune` и `docker volume prune` не используют: на сервере есть чужие контейнеры,
образы и тома. При откате на прежний тег образ соберётся заново.

## Если обновление не удалось

Сначала выясняют, какие миграции нового тега уже применились: команда берёт список миграций
прежнего тега из Git и список применённых миграций из базы и сравнивает их, только если оба списка
получены.

```sh
if known=$(git ls-tree --name-only -r "$old" -- src/core/migrations src/saeckel/migrations) \
  && [ -n "$known" ] \
  && applied=$(docker compose exec -T postgres psql --username=postgres --dbname=hof -At \
      -c "SELECT 'core/' || name FROM core.schema_migrations UNION ALL SELECT 'saeckel/' || name FROM saeckel.schema_migrations") \
  && [ -n "$applied" ]
then
  added=$(comm -13 <(printf '%s\n' "$known" | sed 's|^src/||; s|/migrations/|/|' | sort) \
    <(printf '%s\n' "$applied" | sort))
  if [ -n "$added" ]; then printf 'В базе есть новые миграции:\n%s\n' "$added"
  else echo 'Новых миграций в базе нет'; fi
else
  echo 'ПРОВЕРКА НЕ УДАЛАСЬ: откат не выбирают' >&2
  false
fi
```

- **«Новых миграций в базе нет»** — ни одна новая миграция не применилась, схема базы та же, что у
  прежнего тега: можно вернуть только код (откат A). Это не доказывает, что прежний код понимает
  всё, что успела записать новая версия: если она могла изменить данные так, как прежняя не
  поддерживает, или совместимость не подтверждена, безопаснее откат B.
- **«В базе есть новые миграции»** — эти миграции применились. Прежний образ с такой базой не
  запустится: проверка при старте назовёт их. Миграций вниз нет. Если миграция упала —
  подраздел «Частично применённый набор». Если набор применён весь, а сбой произошёл позже, основной
  выход — исправление вперёд новым образом; при совместимой схеме поведение возвращает новый образ из
  прежнего кода и всех применённых файлов. Откат B — только по решению владельца.
- **«ПРОВЕРКА НЕ УДАЛАСЬ»** — список не получен: PostgreSQL не отвечает (`docker compose ps`),
  неверный `old` (`git tag`) или ошибка запроса. Никакой откат не выбирают, пока проверка не
  пройдёт.

Откат A — только код:

```sh
docker compose stop hof
git checkout "$old"
docker compose up -d --build
```

Откат B — прежний код и копия, сделанная перед обновлением, только по решению владельца. **Всё, что
записали после этой копии, в новой базе `hof` отсутствует** и остаётся только в
`hof_before_restore`. Если новая версия успела поработать, смотрят в Летописи, что внесли после
обновления, чтобы потом записать это заново. Сначала возвращают код:

```sh
docker compose stop hof
copy=$f
git checkout "$old"
docker compose build hof
```

Затем — раздел «Восстановление из копии» целиком; `copy` уже задан и лежит в `~/hof-backups`, поэтому
в шаге 3 строку `copy=…` пропускают. Для ручной копии `.meta` создают по разделу «Проверить копию».
Свежую копию текущего состояния делает тот же шаг 3.

После любого отката в логе `hof` должно быть `info start … migrations=none`. Затем в браузере
проверяют вход, Мешки с остатками и Летопись.

### Частично применённый набор

Каждый файл миграции применяется своей транзакцией, общей транзакции на набор нет, Core идёт раньше
Säckel. Поэтому при сбое на третьем файле первые два остаются применёнными, от третьего следов нет,
автоматического отката набора нет. Набор может содержать миграции нескольких выпусков. Порт
открывается только после всех миграций, поэтому новая версия пользователей не обслуживала.

В логе — `startup_failed error="migration <файл> failed: <причина>"`. Docker перезапускает Hof, и
каждый запуск повторяет упавший файл.

1. Остановить повторы: `docker compose stop hof`. Данные и том не трогают.
2. Выяснить, что применилось: проверка в начале раздела «Если обновление не удалось». Упавший файл
   назван в логе, оставшиеся — файлы папок нового кода после него.
3. Прежний образ не запускают: проверка отклонит его, в базе есть неизвестные ему имена. Образ без
   этой проверки запускать нельзя.
4. Выбрать выход:
   - основной: исправить упавший файл, он нигде не применён, и выпустить новый образ. Hof применит
     остаток. Применённые файлы не меняют. Если причина не в файле, а в окружении, например нет
     места, её устраняют и выполняют `docker compose up -d --no-deps hof`;
   - двор нужен раньше, а применённые файлы совместимы со старым кодом: новый образ из прежнего кода
     и этих файлов, обычным выпуском;
   - оба пути невозможны: Hof остаётся остановленным, решение принимает владелец. Восстановление из
     копии — только отдельным решением, со свежей копией текущего состояния.

`schema_migrations` при этом вручную не меняют.

### Переменные окружения и пароли

- `.env` не хранится в Git. Новые переменные из `.env.example` нового тега дописывают в него сами.
- `docker compose restart` перезапускает контейнер со старыми переменными. Изменённый `.env`
  применяет `docker compose up -d`: Compose пересоздаёт контейнеры, у которых изменилась
  конфигурация.
- `POSTGRES_PASSWORD`, `HOF_CORE_DB_PASSWORD` и `HOF_SAECKEL_DB_PASSWORD` PostgreSQL берёт из
  `.env` только при создании тома. Их правка в `.env` пароли в базе не меняет: `hof` с новым
  значением получит `password authentication failed`. `docker compose up -d` после такой правки
  пересоздаёт и контейнер `postgres` — эти переменные есть и у него; данные остаются в томе, а
  init-скрипт на непустом томе не запускается.
- Пароль роли меняют в базе, затем в `.env`. `\password` спрашивает его дважды, без эха; аргументом
  команды пароль не передают:

  ```sh
  docker compose stop hof
  docker compose exec postgres psql --username=postgres --dbname=hof -c '\password hof_core'
  ```

  Затем записывают тот же пароль в `HOF_CORE_DB_PASSWORD` в `.env` и выполняют
  `docker compose up -d`. Для `hof_saeckel` — так же, с `HOF_SAECKEL_DB_PASSWORD`.

## Диагностика

- **nginx не запускается.** `docker compose up` останавливается на `nginx` с ошибкой монтирования
  `/etc/letsencrypt/live/<домен>`: для `HOF_DOMAIN` из `.env` нет сертификата, или домен не задан
  (`set-HOF_DOMAIN-in-.env`). `certbot certificates` показывает, какие сертификаты есть; выпуск —
  раздел «Установка», шаг 4.
- **502.** nginx не достучался до Hof. `docker compose ps` — работает ли `hof`; если нет —
  `docker compose logs hof` и пункт `startup_failed` ниже. Если работает: в
  `docker compose logs nginx` — адрес `upstream=…` (`upstream=hof` — имя `hof` не находится), а
  `docker inspect --format '{{len .NetworkSettings.Networks}}' hof-hof-1` не должен быть 0. nginx
  переспрашивает адрес `hof` раз в 10 с, поэтому сначала ждут 20 с; 502 остался —
  `docker compose up -d --force-recreate hof` и снова ждут до 20 с.
- **`hof` в статусе `unhealthy`.** Процесс не отвечает на `/healthz`: последние проверки —
  `docker inspect --format '{{json .State.Health.Log}}' hof-hof-1`, причина — в
  `docker compose logs --since 10m hof`. Docker его сам не перезапускает; если процесс завис, его
  перезапускают вручную: `docker compose restart hof`.
- **403 «Запрос отклонён».** Hof отклонил POST: браузер не прислал заголовок `Origin`, или он не
  совпадает с адресом, по которому открыт сайт. В логе `hof` — строка `warn origin_rejected` с полями
  `origin` и `host`. Сайт открывают только по `https://<домен>/`.
- **429 «Слишком много попыток входа. Подождите минуту.»** nginx принимает с одного IP 10 POST в
  минуту на `/login`, `/setup` и `/account/password` и ещё 10 сразу. Через минуту попытки снова
  проходят; в access log nginx у отклонённых — статус 429.
- **`startup_failed`** в логе `hof`: Hof не стартовал, Docker его перезапускает. Текст после
  `error=` называет причину: не задана переменная в `.env`; другая `CURRENCY` или пароль роли —
  раздел «Переменные окружения и пароли»; ошибка миграции после обновления и `applied migrations
missing from` — раздел «Если обновление не удалось».
- **nginx остановлен после продления сертификата.** Флаг `/run/hof-certbot-nginx-hof` на месте —
  post-hook не смог запустить nginx: причина — в `journalctl -u certbot`, повтор —
  `/usr/local/sbin/hof-certbot-hook post`. Флага нет (перезагрузка между pre и post) —
  `docker compose start nginx`. Хук сообщает и о nginx, запущенном без сети Docker: тогда
  `docker compose up -d --force-recreate nginx` и снова `/usr/local/sbin/hof-certbot-hook post`.
- **Порт 80 занят.** certbot сообщает, что не может занять порт 80, или nginx не запускается:
  `ss -tlnp | grep ':80 '` показывает, кто держит порт. Хук освобождает его, только останавливая
  nginx Hof; другой сервис на портах 80 и 443 с этой схемой не совместим.
